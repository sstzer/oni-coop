# 实验 4：同步带宽与丢包影响

> 2026-11-09 补注：这里推荐的"不可靠 UDP + 按确认状态做增量 + 区块"还没有实现，现在全部走 TCP。真实线路（往返约 247 ms，无丢包）实测下够用，见 `architecture.md`「网络」。这里的带宽估算仍然有效。

**问题**：权威端把玩家视野内的格子发给客户端，要多少带宽？丢包、300 ms 延迟下，不同同步策略的画面会旧多少、错多少？

## 三部分
1. **采集**（游戏内，`src/DivergenceProbe`，只改配置）：c02 跑 1 次、300 个 tick（60 s），`snapshotEvery = 1` 每个 tick 存完整格子 + 实体。
2. **离线带宽 / 丢包模拟**（`tools/SyncBench`）：
   ```
   dotnet run --project tools/SyncBench -c Release -- "<run 目录>" [--seeds 20] [--trace netprobe.csv ...]
   ```
   - 视野：以复制人中心为中心的 64×40（正常缩放）、128×80（拉远）、整张地图。
   - 编码：原始 15 B/格；量化（质量 half-float ≈0.05 %、温度 0.05 K、病菌数 log2/8）；只发变化（位图 + 字段掩码 + 温度差值 varint）；Deflate / Brotli。发送间隔 1/3/5 tick（对应速度 1 每秒 5 次、速度 3 每秒 5 次、速度 1 每秒 1 次）。
   - 实体：视野内复制人/小动物，位置 1/32 格，动画/任务变化时才发。
   - 丢包模拟：用真实的逐 tick 状态序列在事件驱动的网络模型里重放。策略：
     - **Keyframe**：每次发整个视野；
     - **DeltaPrevNack**：相对上一次的增量，断链时客户端请求关键帧；
     - **DeltaAcked**：相对客户端最近确认的状态的增量（Quake 3 式）；
     - **ReliableOrdered**：增量走可靠有序流（类 TCP，有队头阻塞）。
     
     包 > 1200 B 时分片，任一分片丢失即整包丢失。网络：你 → 服务器单程 ~160 ms，朋友 ~40 ms；丢包：随机 1/3/5/10/20 %、突发 5 %（平均连丢 4 个）、NetProbe 实测轨迹。
     
     指标：下行 kbps、p95 包大小、显示状态的陈旧度（均值/p95/最大、卡住 > 1 s 的比例）、视觉误差（元素不同或质量差 > 5 % 的格子比例）。
   - 已用合成数据验证趋势合理（`scratchpad/tools/synth_ticks.py`）。
3. **真实网络测量**（`tools/NetProbe`，自包含单文件：`dist/netprobe/linux-x64/netprobe`、`win-x64/netprobe.exe`，副本在 `C:\Users\DELL\Documents\ONI-netprobe\`）：
   ```
   服务器：./netprobe-linux server --port 47800 --token <口令>
   客户端：netprobe client --host <服务器公网地址> --port 47800 --token <口令> --rate 10 --size 1100 --duration 600
   ```
   测下行逐包丢失、连丢长度分布、乱序、RTT 分布、下行时延抖动、上行丢包；输出的 csv 可直接 `--trace` 给 SyncBench 重放。
   安全：只有知道口令、并通过地址挑战（HELLO → CHALLENGE cookie → START）的客户端才会收到数据流；速率 ≤ 60/s、包 ≤ 1400 B、时长 ≤ 1 h、会话 ≤ 4；客户端 10 s 无响应即停。

## 结果（模拟部分，2026-11-08，session_20261108_195459，c02，速度 1，300 tick）
完整报告：`mods/Dev/DivergenceProbe/results/session_20261108_195459/run0_natural/syncbench.md`。

**带宽（每个玩家，仅格子）**
| 视野 | 每 tick 变化的格子（量化后） | 只发变化 + brotli，5 次/s | 死区 2 % / 0.5 K | 死区 5 % / 1 K | 速度 3、仍 5 次/s |
|---|---|---|---|---|---|
| 正常缩放 64×40 | 56.5 % | 143 kbps（3.6 KB/包） | **67 kbps**（1.7 KB/包） | 54 kbps | 171 kbps |
| 拉远 128×80 | 42.0 % | 461 kbps（11.5 KB/包） | 284 kbps | 240 kbps | 538 kbps |
| 整张地图 | 15.3 % | 1.5 Mbps | | | |

视野内的复制人和小动物（约 19–36 个）只要 1–3 kbps，可以忽略。量化（质量 half-float、温度 0.05 K）本身就把原始数据压到约 1/5；"变化的格子"大多是气体温度、质量的细小抖动，死区编码只在客户端的值偏差超过阈值时才发，误差有明确上限，带宽减半。

**丢包与延迟（正常缩放，5 次/s，20 个随机种子）**——"视觉误差"有一个约 7.6 % 的底线：即使不丢包，显示的状态也落后服务器一个 tick（200 ms），这期间气体本来就会变。

| 你这条线（单程 ~160 ms） | 平均旧多少 | 卡住 > 1 s 的时间 | 视觉误差 | 下行 |
|---|---|---|---|---|
| 不丢包（任何策略） | 222 ms | 0 | 7.6 % | 147–164 kbps（关键帧 327） |
| 5 % 随机丢包：**DeltaAcked** | **268 ms** | **0.1 %** | 7.8 % | 167 kbps |
| 5 %：ReliableOrdered（类 TCP） | 432 ms | 3.7 % | 8.6 % | 180 kbps |
| 5 %：DeltaPrevNack | 438 ms | 5.5 % | 8.6 % | 193 kbps |
| 5 %：Keyframe | 309 ms | 0.3 % | 8.0 % | 327 kbps |
| 10 %：**DeltaAcked** | **328 ms** | **0.8 %** | 8.1 % | 171 kbps |
| 10 %：ReliableOrdered / DeltaPrevNack | 733 / 694 ms | 19.6 / 19.7 % | 9.9 / 9.6 % | 223 / 214 kbps |
| 20 %：**DeltaAcked** | 539 ms | 9.7 % | 9.0 % | 179 kbps |
| 突发 5 %（连丢 ~4）：**DeltaAcked** | 248 ms | 0.1 % | 7.8 % | 166 kbps |

朋友那条线（单程 ~40 ms）同样是 DeltaAcked 最好；类 TCP 方案在短延迟下也还可以（重传快），在你这条长延迟线上差很多。

结论：
1. **用"相对客户端最近确认状态的增量"（DeltaAcked），走不可靠 UDP。** 丢包只会让下一个包稍大一点（多 10–15 % 带宽），画面几乎不受影响：10 % 丢包时平均只多旧约 100 ms。类 TCP 的可靠有序流在 300 ms 往返的线路上会队头阻塞，10 % 丢包时有 20 % 的时间卡住超过 1 秒。
2. **死区编码和 DeltaAcked 天然兼容**：服务器知道客户端确认过的状态，就能算出客户端屏幕上偏差多大。
3. **包要切小**：现在一个增量包有 1.7–3.6 KB，会被切成 2–3 个分片，丢包率相当于被放大 2–3 倍。下一步把视野分成若干区块，每块一个独立的 DeltaAcked 流，每个包控制在 1200 B 以内。
4. **预算**：每个玩家正常缩放约 70–170 kbps，拉远约 0.3–0.5 Mbps，**每人 < 1 Mbps**，50 Mbps 上行绰绰有余。
5. 玩家指令（挖、建等）量很小，走单独的可靠通道。
6. 待补：NetProbe 实测你和朋友的真实丢包/抖动后用 `--trace` 重放；眼冒金星地图更大，但按视野同步，每人的开销不随地图大小增长。
